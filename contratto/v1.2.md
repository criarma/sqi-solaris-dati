# CONTRATTO DATI MOTORE SQI ↔ APP SOLARIS, v1.2

Documento consolidato: sostituisce la v1.1 e incorpora i ritocchi V1–V8 di
BT1. È, insieme a `schema/v1.2.json`, **l'unica fonte** per entrambe le
parti. Se testo e schema discordano, è un errore del contratto da
correggere, non una scelta da interpretare.

File che accompagnano questo documento:
- `schema/v1.2.json`: JSON Schema 2020-12, una definizione per file in
  `$defs` (`manifest`, `points`, `forecast`, `potential`, `coverage`);
- `esempi/` (pubblicazione vera) ed `esempi/demo/` (demo): esempi completi,
  generati da `genera_esempi.py`;
- `test_contratto.py`: valida una cartella pubblicata contro lo schema e
  contro i vincoli della sezione 9, e prova che lo schema rifiuti 16 file
  sbagliati. Entrambe le parti lo eseguono nei test.

Negli esempi sono **reali**: geometrie delle zone e del recinto, punti,
orizzonti, orari e azimut del Sole, creste, fasce, impronte, attribuzioni.
Sono **illustrativi**: tela, finestre, poligoni del potenziale e gli
ingressi delle probabilità (le probabilità vengono dalla calibrazione
congelata applicata a quegli ingressi). Le date e i casi della demo negli
esempi sono segnaposto.

## 0. Regole generali

- `schema_version` = `"1.2"`. Un'aggiunta compatibile fa salire la versione
  minore, e l'app ignora i campi sconosciuti. Un cambio incompatibile fa
  salire la versione maggiore: l'app rifiuta i file e lo dice.
- **Codici sconosciuti:** l'app ignora anche i **valori** sconosciuti di
  `flags` e `limiting_factors`. Aggiungere un codice è quindi un'aggiunta
  compatibile.
- Chiavi in inglese, snake_case, ASCII. Nei dati non c'è testo da mostrare,
  solo codici e numeri, con **due eccezioni**: i nomi dei luoghi e i testi
  delle attribuzioni. Questi ultimi sono formule legali e restano nella
  loro lingua (UTF-8, per esempio «ergänzt»).
- GeoJSON secondo RFC 7946. Le coordinate stanno **solo** come
  `[lon, lat]`, con 5 decimali, sia nelle geometrie sia in ogni coppia
  dentro le properties.
- Orari ISO 8601 con offset, nel fuso Europe/Rome, **arrotondati al minuto**
  (secondi `:00`). Date `YYYY-MM-DD` locali. Fa eccezione la corsa del
  modello (`weather_model.run`), che è in UTC con `Z` (sezione 2).
- L'unità sta nel nome della chiave: `_deg`, `_m`, `_km`, `_h`. Gli azimut
  si contano da nord in senso orario, da 0 a 360. Le elevazioni sono
  **apparenti** (con la rifrazione), in gradi, sopra (+) o sotto (−)
  l'orizzonte matematico.
- Probabilità fra 0 e 1, con 2 decimali. Il motore impone
  `p_spectacular <= p_worth`.
- **Punteggio nullo** = punteggio grezzo del motore ≤ 1e-9. «Nullo su tutto
  lo sweep» vuol dire nullo a ciascuna delle 10 elevazioni.
- Il significato di ogni codice sta nella sezione 12.
- Assente non vuol dire zero. Un punto senza previsione non compare nel file
  di previsione. I campi opzionali, quando mancano, sono **assenti** e non
  `null`; l'unica eccezione è `name` in `points`.

## 1. Pubblicazione

- Repository dati separato su GitHub Pages, aggiornato da GitHub Actions con
  un **deploy atomico**: tutti i file in un solo passo.
- Solo `manifest.json` ha un nome fisso. Tutti gli altri file portano nel
  nome un'**impronta del contenuto**, cioè i primi 6 caratteri esadecimali
  dello SHA-256 dei byte del file (es. `forecast_2026-10-15_3f9a2c.json`).
  L'app scarica il manifest sempre fresco, e gli altri file dai nomi che vi
  trova.
- I file citati da un manifest restano pubblicati per almeno 48 h dopo che
  quel manifest è stato sostituito.
- **Una generazione fallita non sostituisce il manifest.** Resta il
  precedente, con il suo `generated_at`, e l'app mostra da quando sono i
  dati.
- **Generazioni** (V1). Le corse ICON-D2 sono disponibili su Open-Meteo
  circa 1.4–1.5 h dopo l'ora nominale (misurato: corsa 03 UTC alle 04:25,
  corsa 09 UTC alle 10:28).

  | ora UTC | corsa | serate generate |
  |---|---|---|
  | 07:45 | 06 UTC | stasera e domani |
  | 13:45 | 12 UTC | stasera; domani resta quella delle 06 UTC |

  Ogni generazione controlla nel `meta.json` del modello che la corsa
  disponibile sia quella attesa. Se non lo è, riprova ogni 15 minuti per al
  massimo un'ora, poi fallisce.
- **Consumo** (BT3): circa 900 chiamate per generazione e 1 800 al giorno,
  il 18% dei limiti gratuiti (giornaliero, orario e mensile). L'uso gratuito
  di Open-Meteo è **solo non commerciale**: una pubblicazione pubblica o
  commerciale richiede una decisione di Cri. Nelle prime settimane ogni
  rifiuto dell'API si registra. Se una settimana ha ≥ 2 generazioni fallite
  per rifiuto, si passa al ripiego: un'operazione pianificata sul PC di Cri.

## 2. manifest.json

```json
{
  "schema_version": "1.2",
  "generated_at": "2026-10-15T09:47:00+02:00",
  "timezone": "Europe/Rome",
  "engine": {
    "version": "4.0.0",
    "form_hash": "<sha256 di forma_congelata.json, 64 esadecimali>",
    "calibration_hash": "<sha256 di calibrazione_congelata.json>",
    "beta": true,
    "validated": false,
    "best_time_bias_corrected": false,
    "calibrated_lead_h_max": 3
  },
  "evenings": [
    {
      "date": "2026-10-15",
      "weather_model": { "name": "ICON-D2", "run": "2026-10-15T06:00:00Z" },
      "lead_time_h": 11,
      "within_calibrated_lead": false,
      "lead_reliability": "unmeasured",
      "forecast": "forecast_2026-10-15_1de60f.json",
      "potential": "potential_2026-10-15_34dd0d.geojson"
    }
  ],
  "points": { "file": "points_<impronta>.geojson" },
  "coverage": { "file": "coverage_<impronta>.geojson" },
  "bands": { "worth": [ ... ], "spectacular": [ ... ], "potential": [ ... ] },
  "diagnostics": { "spectacular_clipped_count": 0 },
  "attribution": [ { "text": "...", "url": "...", "license_url": "...", "scope": "map" } ],
  "demo": false
}
```

### Campi di `engine`

- **`best_time_bias_corrected` = `false`** (V2): `best_time` e
  `best_window` **non** sono corretti per lo scarto medio rispetto al
  fotografo.
- **`calibrated_lead_h_max` = 3** (V1): la calibrazione è stata stimata su
  previsioni a 0–3 h dalla corsa. L'archivio storico di Open-Meteo unisce le
  prime ore di ogni corsa, e ICON-D2 ne fa una ogni 3 h.

### Campi di `evenings[]`

- **`lead_time_h`:** ore intere, arrotondate al più vicino, fra la corsa e
  `sunset_flat_horizon` al `reference_point` della zona. Con più zone si
  prende il **massimo** (le zone differiscono di pochi minuti).
- **`lead_reliability`** (V1): decide il motore; l'app lo mostra.

  | valore | significato |
  |---|---|
  | `calibrated` | `lead_time_h <= calibrated_lead_h_max`: l'anticipo su cui è stata stimata la calibrazione |
  | `measured_close` | anticipo più lungo, misurato sulla conferma ed **equivalente** (criterio sotto) |
  | `measured_degraded` | anticipo misurato e **diverso**: l'equivalenza fallisce **e** un IC al 97.5% esclude la calibrazione perfetta |
  | `unmeasured` | anticipo non ancora misurato, o misura inconcludente |

  **Criterio**, per ciascun anticipo, sui giudizi da soli della conferma
  (`p_worth`; lo spettacolo è descrittivo):
  - curva di ricalibrazione logit P(osservato) = a + b·(logit(p previsto)
    − c);
  - c = −0.1664 è la media di logit(p_worth) sul pool di riferimento, fissata
    prima dell'apertura del sigillo;
  - con calibrazione perfetta a = c e b = 1, quindi lo scarto nel centro è
    **a − c**;
  - IC con errori standard a grappoli per data;
  - `measured_close` se ci sono **almeno 40 date distinte e 150 serate**, e
    l'IC 90% di (a − c) sta dentro [−0.5, +0.5] e l'IC 90% di b dentro
    [0.7, 1.3];
  - altrimenti `measured_degraded` se l'IC 97.5% di (a − c) esclude 0
    oppure quello di b esclude 1;
  - altrimenti `unmeasured`;
  - soglie dichiarate, non tarate;
  - le previsioni ai vari anticipi vengono dalla Single Runs API, corse
    esatte.

  Simulazione con calibrazione perfetta sul pool di riferimento, 8 date per
  sessione come nella sessione 1:
  - con 600 serate e 80 date `measured_close` esce nel **96%** dei casi
    (falsi `measured_degraded` 1.6%);
  - con 300 serate e 40 date scende al **65%**.

  Gli anticipi misurati sono tre: corsa delle 12 UTC dello stesso giorno,
  corsa delle 06 UTC dello stesso giorno (~10 h), corsa delle 06 UTC del
  giorno prima (~34 h). La misura si fa all'apertura del sigillo della
  conferma (criterio registrato in BS2(b)/BT2). **Nella beta, fino ad
  allora, tutte le serate sono `unmeasured`.**
- **`within_calibrated_lead`:** resta, per compatibilità con la v1.1, e
  vale esattamente `lead_reliability == "calibrated"`. Con `false`, l'app
  mostra «previsione a più lungo termine, meno affidabile».
- **`demo_case`:** presente solo se `"demo": true`, e allora obbligatorio.
  Valori: `dull | worth | spectacular | low_deck | clear | sea_of_clouds`.

### `bands` (V7): valori reali

Ogni fascia di `worth` e `spectacular` ha **due coppie di campi**:
- `observed_rate` + `n_calibration`: frequenza osservata nel campione di
  calibrazione (139 serate) e numero di serate in quella fascia. Sono
  sempre quelli del campione;
- `shown_rate` + `shown_rate_source`: **il numero che l'app mostra** e la
  sua fonte.

Ogni fascia ha un `max` **esclusivo**: un valore p sta nella prima fascia
con `p < max`. L'ultima fascia ha `max` = `null`. Le fasce sono in ordine
crescente, gli `id` sono stabili, le parole le mette l'app. **La fascia si
decide sul valore pubblicato** (2 decimali), con la stessa regola dal
motore e dall'app.

**`worth`** (terzili della probabilità calibrata sulle 139 serate di
calibrazione):

| id | max | observed_rate | n_calibration | IC 95% (Wilson) | shown_rate | shown_rate_source |
|---|---|---|---|---|---|---|
| low | 0.1252 | 0.02 | 46 | 0.4–11.3% | **0.09** | **pool_model** (n del pool 1 035) |
| mid | 0.5535 | 0.33 | 46 | 20.9–47.0% | 0.33 | calibration_sample |
| high | null | 0.74 | 47 | 60.5–84.7% | 0.74 | calibration_sample |

**`spectacular`** (75° percentile):

| id | max | observed_rate | n_calibration | IC 95% (Wilson) | shown_rate | shown_rate_source |
|---|---|---|---|---|---|---|
| low | 0.1794 | 0.05 | 104 | 2.1–10.8% | 0.05 | calibration_sample |
| high | null | 0.37 | 35 | 23.2–53.7% | 0.37 | calibration_sample |

**`shown_rate`.** Per ogni fascia si confronta `observed_rate` con la
probabilità calibrata media delle serate del pool di riferimento (4 542
serate vere, mai etichettate) che cadono in quella fascia.
- Se le due differiscono di oltre 0.05, `shown_rate` è quella del pool e
  `shown_rate_source` vale `pool_model`.
- Altrimenti `shown_rate` = `observed_rate` e `shown_rate_source` vale
  `calibration_sample`.
- Il campione di calibrazione aveva 100 zeri del motore su 150, molti più
  delle serate vere, e nella fascia `low` era ottimista: 2% osservato
  contro 9% atteso sulla composizione vera.
- Solo `worth/low` supera la soglia; le altre fasce differiscono di 0.033
  al massimo.

**`potential`** (percentile nella distribuzione congelata, sezione 5):

| id | max |
|---|---|
| zero | 0.4683 |
| low | 0.6012 |
| mid | 0.7341 |
| high | 0.8671 |
| top | null |

`zero` raccoglie le celle dove il punteggio del motore è nullo (il loro
percentile è 0.234). Le altre quattro fasce sono i quartili dei punteggi non
nulli nella distribuzione di riferimento.

- **Arrotondamento:** il valore arrotondato e quello pieno possono stare in
  fasce diverse solo per p in [0.5535, 0.555) e [0.1794, 0.18). È un
  intervallo di 0.0015 al massimo, dichiarato.
- **I tassi osservati sono nel campione:** sono stimati sulle stesse 139
  serate su cui è stata stimata la calibrazione. La conferma li controlla
  fascia per fascia.

### La spiegazione «19% / 2%» (V7+D)

I due numeri non si contraddicono: misurano cose diverse.
- **19%** (18.7%, IC 12.0–27.9%): fra le serate in cui il **punteggio del
  motore** era zero, quasi una su cinque Cri l'ha giudicata «vale la pena».
  Lo zero del motore, quindi, **non è un no**.
- **2%** (1 serata su 46): è la quota di «vale la pena» nella fascia `low`
  della **probabilità calibrata**, nel campione di calibrazione. La
  calibrazione usa due ingressi, il rango del punteggio **e** la nube
  bassa. Sulla composizione vera delle serate la stessa fascia vale circa
  il **9%**, ed è questo il numero che l'app mostra (`shown_rate`).

Uno zero del motore con poca nube bassa riceve p ≈ 0.58, cioè la fascia
`high`. Entra nella fascia `low` solo se la nube bassa supera circa 0.75.
La fascia `low` è quindi il «no» affidabile (circa 9 su 100 valgono
comunque la pena), lo zero del motore non lo è (circa 19 su 100).

Lo stesso vale per gli spettacoli: l'1.9% (IC 0.8–4.7%) delle serate a
punteggio nullo era spettacolare. Erano serate con nube bassa fra 0.6 e
0.75 e l'orizzonte libero.

### `diagnostics` e `attribution`

**`diagnostics`** (opzionale): `spectacular_clipped_count` conta i punti in
cui `p_spectacular` è stato abbassato a `p_worth`.

**`attribution`** (V3): array di `{text, url, license_url, scope}`. Lo
scope dice dove l'app mostra la voce:

| scope | dove | voci |
|---|---|---|
| `map` | sulla mappa | «© OpenStreetMap contributors», ODbL |
| `forecast` | accanto alla previsione | «Weather data by Open-Meteo.com» (CC BY 4.0); **«Datenbasis: Deutscher Wetterdienst, eigene Elemente ergänzt»**, obbligatoria e posta accanto al dato derivato |
| `horizon` | accanto all'orizzonte | nota breve: «Horizon profiles produced using Copernicus WorldDEM-30» |
| `credits` | pagina dei crediti | testo **integrale** dell'art. 6(b) della licenza Copernicus WorldDEM-30 seguito dall'esonero dell'art. 6(c), parola per parola (vedi esempio) |

**Art. 6(d):** né l'app né i dati devono far sembrare il prodotto approvato
da Copernicus, ESA, DLR o Airbus. Niente loghi, e nessuna formula diversa
da quelle sopra.

## 3. points_<impronta>.geojson (statico)

È una FeatureCollection. Ogni Feature ha una geometria Point `[lon, lat]`
e queste properties:

```json
{
  "id": "osm:node/26863828",
  "merged_ids": ["osm:node/1297254731"],
  "name": "Monte Cimone",
  "kind": "peak",
  "elevation_m": 2165,
  "elevation_source": "osm",
  "zone": "appennino_tosco_emiliano",
  "horizon": { "source": "glo30", "start_az_deg": 180, "step_deg": 2, "elevation_deg": [ ... ] }
}
```

- **`id`:** stabile; i preferiti lo usano.
- **`merged_ids`** (opzionale): i belvedere entro 100 m da una cima sono
  fusi nella cima.
- **`name`:** nome OSM grezzo; può essere `null`, che qui è ammesso.
- **`names`** (opzionale): `{ "it": "...", "de": "..." }`.
- **`elevation_source`:** `osm` se viene dal tag `ele`, `dem` se viene da
  GLO-30.
- **`horizon.elevation_deg`:** 90 valori, per gli azimut da 180 a 358
  inclusi.
  - È l'elevazione **apparente** del terreno più alto lungo il raggio, con
    curvatura e rifrazione standard (R_eff = 7/6 R).
  - **Il raggio cresce con la quota:**
    √(2·R_eff·`elevation_m`) + √(2·R_eff·4 810 m), cioè fin dove una cima
    alta quanto il Monte Bianco può ancora spuntare (circa 494 km dal Carè
    Alto).
  - Fonti: GLO-30 fino a 50 km, GLO-90 oltre.
  - **Mai sotto il dip** = −1.76′·√`elevation_m`.
  - **Non è tagliata a zero:** sulle cime è negativa.
  - Esempio: il Carè Alto (3 465 m) a ovest vede le Alpi bergamasche a
    −0.6/−0.8°; il calcolo a 20 km dava −3.8/−6.1°.
  - Questo orizzonte serve per orari e cresta. Il motore usa ancora quello
    a 72 settori e 20 km, perché è stato calibrato con quello.
- **Il file contiene TUTTI i punti**, compresi quelli dentro il recinto
  (solo dati fissi, nessuna previsione).
- **`access`** è riservato alla v2 ed è vietato in v1.2.

## 4. forecast_<data>_<impronta>.json

```json
{
  "date": "2026-10-15",
  "points": {
    "osm:node/1838692508": {
      "sunset_flat_horizon": "2026-10-15T18:31:00+02:00",
      "sunset_azimuth_deg": 258.2,
      "sun_hidden_at": "2026-10-15T18:42:00+02:00",
      "ridge_elevation_deg": -1.73,
      "p_worth": 0.87,
      "p_spectacular": 0.45,
      "best_time": "2026-10-15T18:54:00+02:00",
      "best_window": { "start": "2026-10-15T18:45:00+02:00", "end": "2026-10-15T19:04:00+02:00" },
      "canvas": "high_cloud",
      "limiting_factors": [],
      "flags": []
    }
  }
}
```

**Orari del Sole** (V5): una sola definizione per entrambi. È l'istante in
cui il **bordo superiore apparente** del disco scende sull'orizzonte.
- **Bordo superiore** = elevazione apparente del centro + 0.2666° (il
  semidiametro medio).
- **Rifrazione:** Bennett, in funzione dell'elevazione **apparente** h:
  R′ = 1/tan(h + 7.31/(h + 4.4)) primi d'arco, moltiplicata per
  (P/1010)·(283/(273+T)).
  - P e T sono quelli della previsione al punto, oppure dell'atmosfera
    standard ISA alla quota del punto.
  - Si risolve per iterazione dall'elevazione geometrica.
  - **Elevazioni apparenti negative (cime):** Bennett è tarata per h ≥ 0 e
    qui si **estrapola fino a −2.0°**. Sotto, si tiene il valore a −2.0°.
    L'incertezza è di alcuni primi d'arco, cioè qualche decina di secondi
    sull'istante.
- **`sunset_flat_horizon`:** l'orizzonte è quello **matematico**, cioè
  elevazione apparente 0°. A livello del mare differisce di 22 s dalla
  convenzione standard (centro geometrico a −0.833°).
- **`sun_hidden_at`:** l'orizzonte è quello **reale** del punto. È la
  **scomparsa definitiva**: l'ultimo istante, fra le 10 UTC e quello in cui
  il bordo tocca il dip, in cui il bordo passa sotto la cresta. Il Sole può
  nascondersi e ricomparire.
  - La cresta è `horizon.elevation_deg` interpolato linearmente
    all'azimut del Sole.
  - **Può venire DOPO `sunset_flat_horizon`** (cresta sotto lo zero, sulle
    cime).
  - Se il Sole non sta mai sopra la cresta in quell'intervallo,
    `sun_hidden_at` è **assente** e c'è il flag
    `sun_hidden_all_afternoon`.
- **Test, con tolleranza 1 minuto, tutti superati:**
  - cresta 0 (a 0 m e a 1 300 m) = piatto;
  - cresta −1 a 1 300 m DOPO il piatto (+7.2 min);
  - cresta 6 (−38.7 min);
  - cresta −3 = istante al dip;
  - parete a sud che nasconde il Sole a mezzogiorno;
  - Sole sempre nascosto.

**Altri campi:**
- **`sunset_azimuth_deg`:** azimut del Sole a `sunset_flat_horizon`.
- **`ridge_elevation_deg`:** la cresta (come sopra) a
  `sunset_azimuth_deg`. Può essere negativa.
- **`p_worth`, `p_spectacular`:** probabilità calibrate, modello a due
  ingressi di `calibrazione_congelata.json` (rango del punteggio del motore
  e nube bassa).
- **`best_time`, `best_window`:** dallo sweep del motore: 10 elevazioni
  del centro geometrico da +2° a −5° (2, 1, 0, −0.83, −1.5, −2, −2.5, −3,
  −4, −5), convertite in istanti al punto.
  - `best_time` è il massimo del punteggio.
  - `best_window` è l'intervallo in cui il punteggio è ≥ 80% del massimo,
    con interpolazione lineare.
  - Non sono corretti per lo scarto rispetto al fotografo (V2). L'app
    mostra la finestra, non il minuto.
  - **Se il punteggio è nullo su tutto lo sweep, entrambi sono assenti e
    `canvas` è `none`.** (Il v1.1 voleva `best_window` sempre presente:
    sezione 11.)
- **`canvas`:** la tela al massimo del punteggio, coi codici corretti dal
  motore:

  | codice | significato |
  |---|---|
  | `high_cloud` | strato alto di ICON-D2. Il motore non conosce il genere di nube: per questo non `cirrus` |
  | `mid_cloud` | strato medio |
  | `clear` | tela d'aria: cielo senza nubi da illuminare, solo gradiente |
  | `low_deck_top` | sommità della coltre sottostante; rarissima, 2 stati su 5 868 |
  | `none` | nessuna tela illuminabile |

- **`limiting_factors`:** array ordinato, col fattore principale per primo.
  Non è vuoto **se e solo se** `p_worth` sta nella fascia `low` di `worth`.
  L'app lo presenta come «il motivo principale», non come diagnosi. La
  regola dichiarata (V4) è questa:
  1. **Nube bassa.** Se, ponendo a 0 la sola copertura bassa (stesso
     rango), la probabilità uscirebbe dalla fascia `low`, il primo fattore
     è la nube bassa, con il codice della sua classe:
     - `low_deck_overhead`: almeno un livello di pressione nuvoloso (≥ 50%)
       sopra la quota del punto;
     - `low_cloud`: la posizione non è determinabile.

     Col flag `possible_sea_of_clouds` questo fattore non si mette.
  2. **Causa del motore.**
     - Punteggio nullo: causa nel punto dello sweep col Sole sotto
       l'orizzonte e la tela più accesa.
     - Punteggio non nullo: il termine più basso al massimo, fra tela,
       trasmissione e frazione visibile.

     | causa del motore | codice |
     |---|---|
     | **terreno:** la tela è nell'ombra della cresta, o il raggio di luce verso la tela è fermato dal rilievo | `sun_blocked_horizon` |
     | **nubi:** nubi lungo il cammino della luce verso il Sole (di solito una coltre a ovest, oltre l'orizzonte) che tolgono la luce alla tela | `sun_blocked_clouds` |
     | nessuna tela | `no_canvas` |
     | tela fuori dalla vista | `canvas_out_of_view` |
     | contrasto, luminanza, nessuna causa | `unattributed` |

  Per gli zeri del motore nella fascia `low` il primo fattore è sempre la
  nube bassa: ci arrivano solo con nube bassa sopra circa 0.75.
- **Nube bassa per punto** (V4):
  - Si usano gli 8 livelli di pressione 1000–700 hPa di ICON-D2 nella cella
    del punto, **solo quelli sopra la superficie della cella**. Un livello è
    nuvoloso se la copertura è ≥ 50%.
  - Classi:
    - `low_deck_overhead` se un livello nuvoloso sta sopra la quota del
      punto;
    - `possible_sea_of_clouds` (flag) se tutti i livelli nuvolosi stanno
      oltre 200 m sotto;
    - `low_cloud` altrimenti.
  - 50% e 200 m sono scelte dichiarate, non tarate.
- **`visible_canvas_max_km`** (intero): la distanza massima a cui la tela
  vincente resta visibile sopra la cresta del punto.
  - Formula: R_eff·(√(tan²ε + 2H/R_eff) − tan ε). H è la quota della tela
    sopra il punto al `best_time`; ε è `ridge_elevation_deg`, portata a 0
    se negativa, come nel motore.
  - È la stessa grandezza che il motore congelato usa nel termine di
    visibilità (`CanvasVisibility.usableBand`).
  - Presente solo con `canvas` = `high_cloud` o `mid_cloud`.
  - Il limite vicino del motore è una costante (5 km) e non si pubblica.
  - `visible_canvas_km` (oggetto `{near, far}` della v1.1) resta vietato.
- **`flags`:**
  - `possible_sea_of_clouds`: esclude `low_deck_overhead` e `low_cloud` da
    `limiting_factors`. La scheda dice che il motore non valuta il mare di
    nuvole e che la probabilità probabilmente lo sottostima.
  - `sun_hidden_all_afternoon`: vedi sopra.
- **I punti dentro il recinto sono assenti.**

## 5. potential_<data>_<impronta>.geojson

Poligoni o multipoligoni divisi in fasce: non sovrapposti, con bordi
smussati, ritagliati sulle zone e privati del recinto. Properties:

```json
{ "band": "high", "value_min": 0.7341, "value_max": 0.8671 }
```

- **Scala fissa:** il valore è il percentile del punteggio del motore
  congelato, a **orizzonte libero**, fra le 4 542 serate di riferimento
  (`potenziale_congelato.json`). Le fasce sono quelle di
  `manifest.bands.potential`.
- **Una sera spenta è bassa ovunque.** È un **indice relativo del cielo,
  non una probabilità**. Eredita dalla forma congelata l'effetto del
  contrasto a 0: l'orizzonte libero dà più zeri (46.8%) di quello reale.

## 6. coverage_<impronta>.geojson

Feature di due tipi, con geometria Polygon o MultiPolygon:

```json
{ "kind": "zone", "id": "giudicarie", "name": "Giudicarie", "calibration": "alps",
  "weather_model": "ICON-D2", "reference_point": [10.71073, 46.02981] }
{ "kind": "fenced", "zone": "giudicarie", "until": "2026-12-15" }
```

**Zone** (V8):
- **`giudicarie`**, `alps`: confine della Comunità delle Giudicarie
  (OpenStreetMap, relazione 6535671).
- **`appennino_tosco_emiliano`**, `indicative`: riquadro delle cime OSM con
  nome e quota ≥ 1 600 m nel rettangolo 44.00–44.30 / 10.50–11.05, più
  0.05° per lato. Risulta lat 44.039–44.323, lon 10.451–10.899.
  `indicative` vuol dire che la calibrazione viene da webcam alpine.
- **`weather_model`:** il modello meteo degli ingressi della zona.
  - `ICON-D2`: tutto da ICON-D2, come la calibrazione (Giudicarie).
  - `ICON-D2+ICON-EU`: impronta locale da ICON-D2; le colonne verso il
    tramonto che escono dal dominio ICON-D2 vengono da ICON-EU, nella stessa
    cella e alla stessa ora.
  - Il bordo sud del dominio ICON-D2 sta a circa 43.6–43.7°N, sondato cella
    per cella. Per l'Appennino, nell'arco dell'anno, viene da ICON-EU il
    **13.9%** delle colonne. L'impronta tiene sempre almeno il 95% del suo
    peso dentro ICON-D2.
- **`reference_point`:** centro del riquadro della zona. Serve per
  `lead_time_h`.
- **Geometrie:** il confine completo, **non semplificato** (circa 5 300
  vertici per le Giudicarie), **allargato di 5 m** e agganciato alla
  griglia di 1e-5°.
  - Molte cime stanno esattamente sul confine, che corre sulle creste.
  - Con la semplificazione a 50 m, 10 cime restavano fuori dalla zona di
    1–39 m.
  - Senza l'allargamento, 4 cime recintate stavano sul bordo, cioè fuori
    sia dalla zona sia dal recinto.

**Recinto:**
- **Geometria:** la zona intersecata con l'unione dei cerchi di 30 km
  attorno alle webcam della conferma. Nelle Giudicarie: Malcesine a sud,
  Langenferner e Weissbrunnferner a nord; 132 punti.
- **`until` è una STIMA** (V6). Il recinto cade **all'apertura del
  sigillo** della conferma (300 confronti sigillati), non a quella data. Da
  quel momento il recinto sparisce da `coverage` e i suoi punti ricevono la
  previsione.
- L'app mostra il recinto come «temporaneamente senza previsione».

## 7. Demo

- Ogni serata ha una data reale passata e un `demo_case`.

## 8. Guida (testi lato app, per informazione del motore)

- Le probabilità sono imparate dai giudizi di un solo fotografo su immagini
  di webcam alpine: «il tuo gusto può differire».
- Beta non validata fino all'apertura del sigillo della conferma (stima: 15
  dicembre 2026). Sull'Appennino i valori sono indicativi.
- Il motore non valuta il mare di nuvole.
- Le serate `unmeasured` sono previsioni a più lungo termine di quelle su
  cui il motore è stato tarato.

## 9. Vincoli verificati da test_contratto.py (oltre lo schema)

- **Formati:**
  - impronta nel nome = SHA-256 del contenuto;
  - coordinate a ≤ 5 decimali;
  - orari con l'offset di Europe/Rome valido per quella data.
- **Fasce:** `max` crescenti, ultima `null`, `id` unici, `observed_rate`
  e `shown_rate` crescenti e a 2 decimali, `shown_rate` = `observed_rate`
  quando la fonte è `calibration_sample`.
- **Serate:**
  - data nel nome del file = `date` della serata = `date` dentro il file;
  - `calibrated` solo con `lead_time_h <= calibrated_lead_h_max`.
- **Riferimenti fra file:**
  - ogni punto di previsione esiste in `points`;
  - nessun punto di previsione sta dentro il recinto;
  - ogni zona citata esiste, e ogni punto sta dentro la sua zona (tolleranza
    2e-5°, circa 2 m);
  - il recinto sta dentro la sua zona.
- **Punti:**
  - `horizon.elevation_deg` mai sotto il dip;
  - p a 2 decimali, `p_spectacular <= p_worth`;
  - `limiting_factors` non vuoto se e solo se `p_worth < bands.worth[0].max`;
  - `best_window.start <= best_time <= best_window.end`.
- **Potenziale:** dentro le zone, fuori dal recinto, senza sovrapposizioni.
  Come residuo della griglia è ammessa un'area al massimo pari a perimetro
  × 0.5e-5°.
- **Demo:** presenti i sei casi e almeno una serata non `calibrated`.
- **Mutazioni:** 16 file sbagliati che lo schema deve rifiutare (versione
  1.1, bias `true`, `within_calibrated_lead` incoerente, `demo_case` fuori
  posto, scope sconosciuto, corsa non UTC, `visible_canvas_km`, `cirrus`,
  secondi non nulli, `sun_hidden_at` mancante senza flag, id senza `osm:`,
  `best_window` mancante con tela, `best_time` con tela `none`,
  `visible_canvas_max_km` senza tela da nube, `shown_rate_source` mancante,
  `low_deck_overhead` col flag del mare).
